PROJECT ARK — REBUILD FROM THESE BACKUPS
===============================================================================
This folder is everything needed to produce another Ark. Source tag: v1.0.5
(2026-10-24). Section 5 regenerates it after any change.

Read this before trusting an old copy: the tag above is exactly what is inside
these files. Anything committed after v1.0.5 — the account and bootstrap work,
the new shared-file path and the import ledger, the readiness pages
("What is working" and /api/ready), the network watchdog, the backup and
restore tools with their printed recovery sheet, and ARK Arcade (the game
shelf, player names and game saves) — is NOT in a folder built from that tag.
Regenerate with section 5 before handing a folder to anyone, and check the
date line at the top of REBUILD-ME-ARK.txt against the code you expect: it is
revised whenever the box changes shape.

(A copy lives in the repo as docs/REBUILD-FROM-BACKUP.txt so it travels with
the code; this is the one to keep next to the backup files.)

WHAT IS IN THE FOLDER
  Project-ARK-v1.0.5-src.tar.gz    the repo exactly as tagged (small, plain files)
  Project-ARK-v1.0.5.git.bundle    same repo WITH full history — clone-able
  REBUILD-ME-ARK.txt               the blueprint: build order, 32 traps, gate
  USING-THE-ARK.md                 the plain-English guide for whoever uses it
  README.md                        repo front page / architecture summary
  Project-Ark_bootstrap_architect_deepseek.txt   the original design brief
  SHA256SUMS                       checksums — verify before you trust a copy
  REBUILD-FROM-BACKUP.txt          this file

DELIBERATELY NOT IN HERE
  · the Wi-Fi password (staging/wifi.env) — recreate it, section 1a
  · the Calibre admin password (/etc/ark/calibre-admin) — regenerated by
    re-running phase 30 on the new box
  · the Raspberry Pi OS image (~1.2 GB, re-downloaded by the flash script)
  · the library content (~21 GiB of .zim + books) — cheapest to re-fetch, or
    copy it from a running box, section 3
  · a copy of the household's own records — that is a different artefact: run
    `sudo ark-backup --to /srv/ark/backup` on the running box and keep the
    dated folder (notes, shared files, accounts, book-import list, named
    players' game saves) next to these files. It is what
    `sudo ark-restore --from <folder>` reads.

1. FROM THE TARBALL → a brand-new Ark (the normal path)
------------------------------------------------------------------------------
  mkdir -p ~/Survival-Pi-new
  tar xzf ~/Downloads/Project-Ark/Project-ARK-v1.0.5-src.tar.gz \
      -C ~/Survival-Pi-new --strip-components=1
  cd ~/Survival-Pi-new

  # 1a. the one secret the backup cannot hold — the household Wi-Fi
  cat > staging/wifi.env <<'ENV'
  WIFI_SSID="TheirNetwork"
  WIFI_PASSWORD="their password"
  WIFI_COUNTRY="GB"
  ENV
  chmod 600 staging/wifi.env
  # optional: WIFI_FALLBACK_SSID / WIFI_FALLBACK_PASSWORD, and further slots
  # WIFI_SSID_1 / WIFI_PASSWORD_1 if the Pi moves between places

  # 1b. render the first-boot script (embeds the PSK, chmod 700)
  bash scripts/make-firstrun.sh

  # 1c. flash — raises a Touch ID/password dialog, and refuses to write
  #     anything that is not an external 100-270 GB card (rule 2)
  bash scripts/01-flash.sh

  # 1d. card into the Pi, power on, wait for it to appear (3-5 min)
  bash scripts/02-wait-for-pi.sh

  # 1e. install everything on the Pi (runs in the background there, so a
  #     dropped Wi-Fi link cannot kill it; 35-60 min, log streams back)
  bash scripts/03-provision.sh

  # 1f. the gate — no ✗, plus the closing line "everything a visitor touches
  #     is working" (the number of checks grows as the box does; read the ✗
  #     column, not the total)
  bash scripts/03-provision.sh --only 90-verify
  cat logs/ark_status.json

  # 1g. claim the owner's door — through the tunnel, on the Mac, once
  ssh -N -L 8444:127.0.0.1:8444 pi@ark.local
  #    leave that running, open https://localhost:8444/admin
  #    user: admin
  #    temporary password: cat /srv/ark/api/data/bootstrap-password
  #    (the box then asks for your own password; docs/ADMIN.md section 2)

  Content then fills itself in: the downloader walks the queue smallest-first
  (on the Pi: sudo tail -f /srv/ark/logs/zim-download.log). The portal strip
  shows the live percentage while it does.

3. FROM THE RUNNING PI → when no backup exists, the box IS the backup
------------------------------------------------------------------------------
  # 3a. code + config (~600 KB; the config holds the Calibre admin password)
  rsync -az --rsync-path='sudo rsync' pi@ark.local:/srv/ark/src/ ./ark-src/
  rsync -az --rsync-path='sudo rsync' pi@ark.local:/etc/ark/    ./etc-ark/

  # 3b. content (~21 GiB; skip it if the new box can download its own)
  rsync -az --rsync-path='sudo rsync' pi@ark.local:/srv/ark/kiwix/ \
      ./kiwix-content/
  rsync -az --rsync-path='sudo rsync' pi@ark.local:/srv/ark/calibre-library/ \
      ./calibre-content/
  rsync -az --rsync-path='sudo rsync' pi@ark.local:/srv/ark/vault/ ./vault-content/

  # 3c. put it on the new box, then let the installer re-index and verify
  rsync -az --rsync-path='sudo rsync' ./kiwix-content/ \
      pi@ark.local:/srv/ark/kiwix/
  ssh pi@ark.local 'sudo chown -R pi:pi /srv/ark/kiwix'
  ssh pi@ark.local 'sudo bash /srv/ark/src/install-ark.sh --only 50-kiwix'
  ssh pi@ark.local 'sudo bash /srv/ark/src/install-ark.sh --only 90-verify'

  # 3d. if those .zim files came from a box that was switched off mid-download,
  #     look for hole-filled files before trusting them (trap 25):
  ssh pi@ark.local 'cd /srv/ark/kiwix && for f in *.zim; do
      a=$(du -B1 "$f" | cut -f1); s=$(stat -c %s "$f");
      [ "$a" -lt $(( s - s/50 )) ] && echo "SUSPECT $f"; done'

  # 3e. what people put in the File Box, plus the record of what has already
  #     been imported (the ledger is what stops a rescan re-adding every book)
  rsync -az --rsync-path='sudo rsync' pi@ark.local:/srv/ark/drop/files/ ./drop-files/
  rsync -az --rsync-path='sudo rsync' \
      pi@ark.local:/srv/ark/calibre-incoming/.imported.json ./drop-files/

  #     putting them back: the File Box folder must exist and belong to pi; the
  #     stored names are random, so the portal's existing links keep working
  ssh pi@ark.local 'sudo install -d -o pi -g pi -m 775 /srv/ark/drop/files'
  rsync -az ./drop-files/ --exclude '.imported.json' pi@ark.local:/srv/ark/drop/files/
  rsync -az ./drop-files/.imported.json \
      pi@ark.local:/srv/ark/calibre-incoming/.imported.json
  ssh pi@ark.local 'sudo chown -R pi:pi /srv/ark/drop /srv/ark/calibre-incoming'

4. WHAT "GOOD" LOOKS LIKE WHEN IT IS DONE
------------------------------------------------------------------------------
  · no ✗ in the gate, and logs/ark_status.json pulled back to the Mac
  · the owner's door behaves: curl -sk https://ark.lan:8443/admin answers with a
    sign-in page, curl -s http://ark.lan/admin answers 404, and the first claim
    is done (docs/ADMIN.md)
  · http://ark.lan answers on a phone joined to the same network
  · /kiwix/ lists collections, /books/ shows covers, /vault/ lists the guides
  · `curl -s http://ark.lan/api/ready` answers **200** and names every part; a
    503 is not a failure by itself — read `blocking` and each part's `reason`
  · the owner's **What is working** page agrees with that answer, and stopping
    one reader on purpose turns its row to *Not ready* with the next step
  · the home strip counts collections/books/guides and, while content is still
    arriving, shows "<n>% of <name> (x GB of y GB)", the whole-queue share, and
    a time left only when the box measured a real speed
  · the File Box accepts a file and refuses an empty one with a readable
    sentence; uploading the same filename three times leaves three entries and
    three files in /srv/ark/drop/files with nothing left in /srv/ark/drop/tmp
  · a book dropped in the File Box is on the shelf within a minute and its File
    Box link still downloads afterwards
  · /arcade/ lists the games and a guest can play one; the page carries no
    http:// or https:// asset address, so it still works with the internet
    unplugged
  · https://ark.lan:8445/arcade/player answers with the box's certificate; a
    named player can keep a save, export the saves as one zip, and put them back
  · sudo ark-backup --to /srv/ark/backup writes one dated folder; --verify
    re-reads every byte; http://ark.lan/recovery.txt opens and can be printed
  · hotspot test: sudo ark-mode test 180 → join "The-Ark-Offline" → the phone
    opens the portal by itself → after 3 minutes it returns to the home Wi-Fi

5. REFRESH THE BACKUP (after any change — 30 seconds, no card)
------------------------------------------------------------------------------
  cd ~/Survival-Pi
  git status --short            # must be empty; commit first if it is not
  git add -A && git commit -m 'what changed'
  V=v1.1.0                      # the NEXT version; never move v1.0.5
  git tag "$V"                  # no -f: a moved release tag breaks every copy
  git push origin feature/admin-hardening "$V"

  D=~/Downloads/Project-Ark
  git archive --format=tar.gz --prefix=Project-ARK/ -o "$D/Project-ARK-$V-src.tar.gz" HEAD
  git bundle create "$D/Project-ARK-$V.git.bundle" --branches --tags HEAD
  cp docs/REBUILD-ME-ARK.txt docs/USING-THE-ARK.md README.md "$D/"
  ( cd "$D" && shasum -a 256 Project-ARK-*.tar.gz Project-ARK-*.git.bundle > SHA256SUMS )
  ( cd "$D" && shasum -a 256 -c SHA256SUMS )

  Last step of any release: this sheet names the version in ~10 places, so
  refresh it too — copy the new docs in, then `sed -i '' "s/$OLD/$V/g"` on the
  copy in $D, and delete the previous tar.gz/bundle.

  Public mirror: bash scripts/publish-github.sh (needs a PAT in
  ~/.config/ark/gh.token, chmod 600 — the token stays out of git and the URL).

  Notes from the first run of this: `--branches --tags` instead of `--all` keeps
  the agent's internal checkpoint refs out of the backup; and keep the folder
  flat with exactly one tar.gz + one bundle — delete the older pair once the new
  one verifies, because two "latest" files is how a backup stops being trusted.

  Notes from later sessions (cost hours the first time, seconds after that):
  · Tool calls issued together run in parallel. A `pkill` or a service restart
    will race the probe that was supposed to observe it, and two commands that
    bind the same port in one batch fail in a way that looks like a code bug.
    Sequence anything that changes state first, observe second.
  · A commit message containing an apostrophe must go through a file:
    `git commit -F /tmp/msg.txt`. Inline, the shell re-quotes it and git reads
    the rest of the sentence as pathspecs ("did not match any file(s)").
  · Run the tests before tagging anything: `.venv/bin/python -m pytest`. They
    use throwaway databases, so they never touch the live library, and they do
    not need a Pi.
  · Work committed after the tag is NOT in the archive above. Tag the next
    version first, then regenerate this whole set — a backup that silently
    predates the code is worse than no backup.

6. HANDING IT TO SOMEONE ELSE (or to another assistant)
------------------------------------------------------------------------------
  Give them this folder plus REBUILD-ME-ARK.txt and say: "build me one of
  these". The blueprint opens with six questions (who it is for, card size,
  whose Wi-Fi, ...) and is written so an agent with no memory of this project
  can do it. The traps section is what saves the hours.
