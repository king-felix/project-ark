================================================================================
1. WHAT YOU ARE BUILDING
================================================================================

A Raspberry Pi 4 that carries a library into places with no internet. It
broadcasts its own open Wi-Fi, serves a portal at http://ark.lan, and works
with the router unplugged, the phone on aeroplane mode, or the grid down.

It is not a demo. The acceptance test is: a non-technical person, handed the
box with no instructions, can find something useful within 60 seconds; and a
cold boot with nobody present produces a working hotspot and portal with no
human intervention at all.

Doors on the box (once built):

  /                     portal: one search box, big plain-English cards
  /search?q=…           one search covering encyclopedias + manuals + books
  /kiwix/               offline library (Wikipedia, medical, repair, food…)
  /books/               the book shelf (EPUB/PDF, read in browser or download)
  /vault/               11 survival manuals + repair guides, each printable
  /board                message board, anyone can post, no login
  /files                File Box: anyone can drop a file in (2 GB each); books auto-shelve
  /arcade/              games shelf: small openly licensed homebrew, played in the browser
  /help.html            how it works, in plain words
  /status.json          machine-readable health (also mirrored in the portal)

A game shelf sits beside the library. A visitor needs no name to play; an
optional player's name (different tables, different cookie, different origin)
keeps game saves on the box and is never an administrator account. Playing a
game is the one place JavaScript is required; the shelf list, every reading
page and every admin page still work without it.

And one door that is NOT on the portal: the owner's door, on its own TLS
address, for whoever maintains the box.

  https://ark.lan:8443/admin   sign-in + accounts + audit + Community + Games
                               (404 on port 80); "What is working" — every part,
                               ready or not, with the plain reason and next step
  https://ark.lan:8445/arcade/ the player's own TLS origin: sign in for saves,
                               export/import; 404 for /admin; never on port 80

Asking a script "is it usable?" has one honest answer: /api/ready, 200 only when
every part a reader needs actually answered, 503 with the reasons when one did
not.  /api/health is liveness only ("the backend answered") and says so in its
own body — it is never a verdict.

================================================================================
2. WHO IT IS FOR (this drives every design decision)
================================================================================

Someone who has never heard the words Kiwix, ZIM, Calibre, OPDS, FastAPI,
nginx, systemd, SQLite, port, or localhost — and who may be reading it on a
cracked phone, in the dark, on battery, with cold hands.

Therefore:
  · Dark by default (#000000 true black — OLED screens, torch discipline).
  · Big type (>=16 px), big targets (>=44 px), no hover-only affordances.
  · No JavaScript on any critical path. Search and every link work with JS off;
    playing a game is the one deliberate exception.
  · No accounts and no logins for a reader, ever — nothing on the public portal
    asks who you are. (The machine itself has one owner's door, on a separate
    TLS address the portal never serves; a visitor can ignore it forever. A
    player name for game saves is optional, on its own TLS origin, and is not
    an account on the box either.)
  · Every section has a one-line plain-English description and a "How to use".
  · Buttons say what happens: "Tap here to read this in your browser" — never
    "Open ZIM viewer".
  · Never show a raw error, a stack trace, or an HTTP status code to a visitor.

================================================================================
3. NON-NEGOTIABLES (each one has already been paid for; do not relax them)
================================================================================

 1. ZERO-TOUCH BOOT. Every unit is `systemctl enable`d AND `--now` started.
    A cold boot with nobody present yields hotspot + portal. Guaranteed by a
    failsafe unit, not by hope.
 2. BANNED WORDS in anything a visitor can see: Kiwix, ZIM, Calibre,
    Calibre-Web, OPDS, FastAPI, nginx, systemd, SQLite, APK, port, localhost,
    daemon, service, proxy. Approved words: Offline Library, Books, Manuals,
    Guides, Q&A, Repair Guides, Message Board, File Box, Planting Calendar,
    Download, Read in Browser, Search.
 3. ANONYMOUS READING. Browse, read, download, upload, post, play — no login
    for any of it. Two exceptions, both on their own TLS origins and never on
    the public portal: administration (:8443, its own accounts, 404 on :80, no
    reachable default password while unclaimed) and an optional player name for
    game saves (:8445, separate tables and cookie, 404 for /admin). Reading must
    keep working even if either store is broken.
 4. THE CARD IS NEVER FILLED. A free-space reserve is enforced by the
    downloader itself (default 12 GiB). Anything that would breach it is
    skipped, logged and retried later — never silently dropped.
 5. IDEMPOTENT PHASES. Re-running any phase must not corrupt or duplicate.
    Every file write is content-compared first; every HTML injection is
    marker-guarded; every service start tolerates "already running".
 6. NO GUESSING ABOUT DISKS. Never write to a device unless it is external and
    physical, 100-270 GB, Internal=false, and appears in
    `diskutil list external physical`. Zero matches = abort loudly.
 7. NOTHING SECRET IN THE REPO. Wi-Fi PSKs live in chmod-600 files, are
    embedded into a chmod-700 first-boot script, and that script is deleted
    after first boot.
 8. PLAIN BASH + SYSTEMD + NGINX + PYTHON. No Docker, no Kubernetes, no
    Node, no build step. One person must be able to debug it over SSH with
    `journalctl` and `curl`.
 9. EVERY CLAIM IS PROVEN BY OUTPUT. "Implemented" is not "works". A phase is
    done when a command's output says so — printed, not asserted.
10. LF LINE ENDINGS everywhere under pi/ and staging/. CRLF breaks shebangs
    on Linux and produces the classic "No such file or directory" for a file
    that plainly exists.

================================================================================
4. THE KIT + THE VERSIONS THAT MATTER
================================================================================

  Hardware   Raspberry Pi 4B, 8 GB RAM (4 GB works for mini profile)
             microSD 128 GB minimum, 256 GB for the full reference set
             Pi 4B needs the official 3 A supply — brownouts corrupt cards
  OS         Raspberry Pi OS **Lite 64-bit, Debian 13 trixie** (Bookworm works)
             hostname `ark`, user `pi`, SSH key auth + password (first boot)
  Mac side   macOS, zsh/bash, Raspberry Pi Imager CLI for flashing
  Packages   nginx, python3 + venv, calibre (8.5 on trixie), calibre-web,
             kiwix-tools, wget + curl (single-stream fetchers), sqlite3,
             avahi-daemon, dnsmasq-base, network-manager,
             weasyprint (HTML→PDF for the printable guides)

  VERSION TRAP: Debian trixie ships **calibre 8.5, schema 26**. A Windows or
  macOS Calibre newer than that writes schema 27+. Never refuse on the number
  alone — see trap 11.

5. THE SHAPE OF IT
================================================================================

On the Pi, everything the Ark owns lives under /srv/ark:

  /srv/ark/src              git-pushed copy of this repo (pi/, scripts/, docs/)
  /srv/ark/portal           static portal (index.html, help.html, assets/)
  /srv/ark/kiwix            .zim bundles + library.xml (the source of truth)
  /srv/ark/calibre-library  the book shelf's database and cover art
  /srv/ark/drop/files       File Box (the only folder nginx serves); every upload
                            gets a random stored name, links never overwrite
  /srv/ark/drop/tmp         half-arrived uploads, reconciled at start, never served
  /srv/ark/calibre-incoming/done   where auto-imported books retire to
  /srv/ark/calibre-incoming/.imported.json  sha256 ledger: one import per content
  /srv/ark/imported-library one-off staging area for a whole-library adopt
  /srv/ark/vault            manuals, guides and generated PDFs
  /srv/ark/logs             zim-download.log, import logs, status receipts
  /srv/ark/api/data/ark.db  the owner's door: accounts, sessions, audit rows
  /srv/ark/api/data/ark.installed  marker kept OUTSIDE the database, so a wiped
                            database means "recovery required", never a new
                            default password
  /etc/ssl/ark/             ark-admin.crt + ark-admin.key (0600 root:root)
  /etc/ark/ark.env          operator settings (single place to change things)
  /etc/ark/zim-queue.tsv    resolved download queue (pinned URLs + sizes)
  /etc/ark/zim-profile      mini | core | full
  /etc/ark/mode             auto | home | hotspot

Services (all enabled AND started; this is the cold-boot contract):

  nginx.service               :80    the only port a visitor touches
                              :8443  the owner's door (TLS, /admin only)
                              :8444  loopback-only setup listener, unclaimed box
                              :8445  the player's TLS origin (/arcade only)
  ark-kiwix.service           :8081  kiwix-serve --urlRootLocation=/kiwix
  ark-calibre.service         :8083  calibre-web, served under /books
  ark-api.service             :8085  FastAPI: /api, /search, /board, /files, /arcade
  ark-boot-guard.service      —      failsafe: no home net → raise hotspot
  ark-net-watch.service/.timer —     every minute: link lost → hotspot, back
                                     → home; never drops a connected reader
  ark-arcade-discover.service/.timer — 15 min after boot, then weekly: seed + discover
  ark-zim-downloader.service  —      background, resumable content queue
  ark-book-import.path/.service —    watch drop/files, shelve books in seconds
  ssh, NetworkManager, avahi-daemon, and dnsmasq ONLY via NM ipv4.method shared
                                     (never enable the standalone dnsmasq unit)

nginx is the reverse proxy and holds the captive-portal traps: every
connectivity-check URL (/generate_204, /hotspot-detect.html, /ncsi.txt,
/connecttest.txt, /library/test/success.html, /canonical.html, /redirect, …)
302s to http://ark.lan/?captive=1 so phones believe they are online and the
popup resolves to the portal instead of a "no internet" dead end.

6. BUILD ORDER (each phase ends with a proof, not a claim)
================================================================================

  On the Mac:
  00  staging/       wifi.env (chmod 600) → make-firstrun.sh → firstrun.sh (700)
                     the pi password is generated there too, into
                     staging/pi-password.txt (600) — no default password exists
                     in the repo, so every Ark gets a different one
                     WIFI_EXTRA_PROFILES in the same file seeds networks that
                     are NOT the home router (another house, a phone hotspot):
                     one `id|ssid|password|priority` per line, priorities below
                     the home slots' 20/10/5 so home still wins at home
  01  flash          assert the SD card with lib-disk-guard, then flash
  02  wait-for-pi    poll SSH until the Pi is up on the home LAN
  03  provision      rsync the repo to /srv/ark/src, then run pi/install-ark.sh
                     with --only <phase> to re-run one phase safely

  On the Pi (pi/steps/NN-name.sh, sourced by pi/lib/common.sh):
  10  base        apt update/upgrade, packages, timezone, hostname, `pi` user,
                  venv for the API, /etc/ark skeleton. Proof: versions printed.
  20  storage     /srv/ark tree, ark.env, mode file, permissions, disk headroom
                  warning. Proof: tree + free space.
  30  calibre     calibre-web install, empty library created pi:pi 775, drop
                  folders, ark-book-import path unit, ark-import-books and
                  ark-import-calibre-library helpers. Proof: HTTP 200 on :8083
                  AND a book dropped into drop/files appears within 60 s.
  40  vault       copy manuals + guides, render each to PDF with weasyprint,
                  inject the "Print this page (PDF)" link into every page.
                  Proof: 11 pages 200, 11 PDFs 200, link present exactly once.
  50  kiwix       kiwix-tools, catalog.tsv, ark-zim-resolve (catalogue → pinned
                  queue), ark-kiwix-library (/kiwix path + library.xml),
                  ark-zim-download (flock, resume, size guard, rate limit),
                  systemd unit. Proof: :8081/kiwix/ answers, queue written.
  60  portal      static portal, API venv, systemd unit, nginx site, captive
                  endpoints, print styles, help page, the arcade modules/player,
                  the first game shelf and its weekly discovery timer.
                  Proof: every route 200/302, including /arcade/ and its player.
  65  admin       the owner's door: scrypt accounts, forced first password,
                  nginx :8443 management origin (+ :8444 loopback setup while
                  unclaimed) and the :8445 player origin, self-signed certificate,
                  root-only recovery command.
                  Proof: :80/admin is 404, :8443 needs TLS and a sign-in,
                  :8444 only answers through the tunnel, recovery is 0700 root,
                  :8445 answers /arcade/player and 404 for /admin.
  70  network     NM hotspot profile (ipv4.method shared, 10.42.0.1/24, ch 6),
                  dnsmasq-shared.d wildcard for ark.lan/ark.local, boot guard,
                  ark-mode (auto|home|hotspot|test), and the watchdog
                  (ark-net-watch + .timer, phase 70 enables and starts it).
                  Proof: profile exists, guard active, timer enabled AND active,
                  `ark-net-watch --dry-run` prints what it sees, and
                  `ark-mode test` works when a human tries it.
  95  backup      ark-backup + ark-restore on the shared ark_bundle.py,
                  /srv/ark/backup (0700), the recovery sheet at
                  /srv/ark/RECOVERY-SHEET.txt and /srv/ark/portal/recovery.txt,
                  then `ark-backup --dry-run` as the proof. No timer, on
                  purpose: a nightly copy can fill the card the box reads.
  90  verify      the gate (section 9) + JSON receipt back to the Mac.

  Rule: a phase that cannot print its own proof is not finished. Write the
  proof line first, then make it true.

  ARC: build the empty box first and prove the portal works with nothing in
  it. Content arrives afterwards, in the background, for hours. Never let a
  multi-hour download sit between you and "does the page load".

================================================================================
7. THE TRAPS (symptom → cause → fix). This section is the expensive part.
================================================================================

 1. FLASHING THE WRONG DISK
    Symptom: nothing; then a destroyed Mac.
    Cause: /dev/disk2 is not "the SD card", it is "whatever is second today".
    Fix: guard function in scripts/lib-disk-guard.sh. Requires ALL of:
    appears in `diskutil list external physical`; identifier is not disk0/disk1;
    diskutil info -plist shows Internal=false and Ejectable/RemovableMedia=true;
    size 100-270 GB; not a synthesized container; not a disk image. Zero
    candidates → exit 2 with a loud message. Print the resolution to the human
    and require the guard to pass before any write.

 2. sudo HANGS IN AN AUTOMATED SESSION
    Symptom: the flash step waits forever, or fails with "a terminal is
    required".
    Cause: an agent has no TTY for a password prompt.
    Fix: write a helper .sh to disk, then
      osascript -e 'do shell script "/bin/bash /path/helper.sh" with administrator privileges'
    That raises a native Touch ID/password dialog. Never try to pipe a password.

 3. FIRST-BOOT SCRIPT LEFT BEHIND WITH THE WI-FI PASSWORD
    Symptom: none until someone reads the card.
    Cause: firstrun.sh still on the boot partition contains the PSK.
    Fix: generate from a template with the PSK substituted, chmod 700, run once
    at first boot, then delete itself AND remove its hook from cmdline.txt.
    wifi.env stays chmod 600 and gitignored.

 4. dnsmasq AND NetworkManager FIGHTING
    Symptom: hotspot comes up, clients get no address, or ark.lan does not
    resolve only while the AP is up.
    Cause: the standalone dnsmasq unit and NM's shared-mode dnsmasq both bind
    :53.
    Fix: `systemctl disable --now dnsmasq`; let NM's ipv4.method=shared own
    DHCP+DNS; put the wildcard (address=/#/10.42.0.1) in
    /etc/NetworkManager/dnsmasq-shared.d/ so it exists only while the AP does.

 5. CAPTIVE POPUP SHOWS "NO INTERNET"
    Symptom: phone joins the Wi-Fi, nothing opens, or a dead "Sign in" sheet.
    Cause: the OS connectivity probe gets a 200 with unexpected content.
    Fix: 302 every known probe URL to the portal with ?captive=1 (list in
    section 5), and give the portal a one-line "if this opened in a Sign in to
    Wi-Fi sheet, close it and open http://ark.lan" plus a Copy Address button.

 6. KIWIX SERVES 404 FOR EVERYTHING
    Symptom: http://ark.lan/kiwix/ loads, every link inside it 404s.
    Cause: kiwix-serve is behind a sub-path and does not know it.
    Fix: start it as `kiwix-serve --urlRootLocation=/kiwix --port 8081
    --library /srv/ark/kiwix/library.xml`. Verify by fetching one known article,
    not just the root: root 200 + article 404 means the root location is wrong.

 7. A BROKEN .ZIM THAT LOOKS FINE ON DISK
    Symptom: a bundle is 1.4 GB, the file exists, but kiwix logs
    "unreadable bundle" and the entry vanishes from the library index.
    Cause: a truncated or corrupt download; size alone cannot tell you it is
    valid — and a partial file has a plausible size.
    Fix: the single source of truth for "present" is **library.xml**, i.e. what
    kiwix-serve itself managed to index. `have_zim` must return true only if the
    bundle is listed there. Rebuild the index bundle-by-bundle when the bulk
    build fails, so one bad file does not hide the other 15.

 8. TWO DOWNLOADERS WRITING THE SAME .part
    Symptom: disk fills with nonsense, or the fetcher dies with a file error,
    usually after a reboot or a manual restart.
    Cause: systemd restart plus a leftover foreground run; the old process keeps
    writing into the old inode after the file was renamed.
    Fix: `flock -n` on a lock file at the top of the downloader; if the lock is
    held, log and exit 0. Also never `mv` a .part that a live downloader owns.

 9. TRUSTING THE CATALOGUE'S SIZE
    Symptom: "complete" files that are 3% short, or endless re-downloads.
    Cause: published files get republished; the catalogue length is stale.
    Fix: accept when got >= expected - 1%; keep the .part when short (so the
    next attempt resumes rather than restarting); record a .done stamp per
    bundle so completed work is never redone.

10. FILLING THE CARD
    Symptom: the box works until one day nginx cannot write a log and the
    filesystem goes read-only.
    Cause: a 119 GiB full-encyclopedia row on a 128 GB card.
    Fix: MIN_FREE_GIB (default 12) checked before every file; skip + log +
    retry later. Settings must be reachable by the unit
    (`EnvironmentFile=-/etc/ark/ark.env`) — a documented knob that nothing
    loads is worse than no knob.

11. "NEWER SCHEMA" REFUSAL ON AN EXISTING CALIBRE LIBRARY
    Symptom: adopting a Windows/Mac Calibre library aborts with a version
    complaint even though the books are ordinary EPUBs.
    Cause: schema number is not a compatibility proof. Calibre 8.5 (schema 26)
    reads AND writes a schema-27 database perfectly well when the change was
    additive.
    Fix: probe instead of guessing — copy just metadata.db to a temp dir and run
    `calibredb --with-library <tmp> list --limit 1`. If it opens, carry on and
    say so; if it does not, refuse and offer `--force`. Never test on the live
    or source database.

12. COPYING A LIBRARY FROM WINDOWS
    Symptom: 4,000 files, 5.7 GB, and either the copy takes days or the books
    land flat with no metadata.
    Cause: SMB per-file overhead; and people copy only the book folders.
    Fix: copy the WHOLE "Calibre Library" folder (metadata.db + author folders +
    .calnotes). Use tar over ssh or a USB stick — 10-100x faster than SMB for
    many small files. In PowerShell, wrap paths in single quotes and double any
    apostrophe inside a name (O'Brien → 'O''Brien'). Prove completion by
    comparing file count and total bytes, not by watching a progress bar.

13. LIBRARY PERMISSIONS THAT BREAK THE SHELF
    Symptom: the shelf loads, covers are broken, or adding a book fails with
    "permission denied" in the unit log.
    Cause: calibre-web runs as `pi` but files are root:root, or .calnotes is
    missing.
    Fix: chown -R pi:pi, chmod 775 on the library root and .calnotes, 644 on
    files. Calibre complains (harmlessly) if .calnotes is absent — create it.

14. AUTO-IMPORT GRABBING A HALF-COPIED FILE, OR IMPORTING THE SAME BOOK FOR EVER
    Symptom: a book appears on the shelf and cannot be opened; or the same book is
    added again on every scan; or a download link in the File Box stops working.
    Cause: the watcher fires while the copy is still in progress; `done/` is
    rescanned; the importer moves the File Box copy away after importing it.
    Fix: a systemd .path unit (PathModified on drop/files) triggers a .service
    that waits for size to stop changing for ~3 s before importing. Keep a sha256
    ledger (`calibre-incoming/.imported.json`) and skip any content already in it,
    so a rescan is free and a renamed re-drop is a no-op. Never rescan `done/`,
    and never move a file out of `drop/files` — that is the folder the portal
    links to. Debounce, fingerprint, then act.

15. CALIBRE-WEB BEHIND /books
    Symptom: the shelf loads at /books/ but every cover, style and link points
    at the site root and 404s; or login redirects land on /login.
    Cause: the app is not told it lives under a sub-path.
    Fix: set the app's URL prefix/SCRIPT_NAME to /books, proxy_pass with the
    path intact, and send X-Forwarded-Prefix. Proof: not just /books/ 200, but a
    cover URL and one book detail page also 200.

16. FASTAPI BEHIND /api
    Symptom: /api/status works, /api/docs loads a broken Swagger page, redirects
    drop the prefix.
    Cause: the app does not know its external prefix; nginx strips it.
    Fix: uvicorn with --root-path /api, proxy_pass to the app root without
    stripping, and never hardcode absolute links in HTML responses. Proof:
    /api/status 200 AND one HTML form POST (board / file upload) returns 303.

17. THE FILE UPLOAD THAT WORKS IN TESTS AND FAILS IN REAL LIFE
    Symptom: a 60 MB PDF upload returns 413, or the File Box accepts a file and
    the API sees zero bytes; or two people uploading "photo.jpg" in the same
    minute end up with one file and two list entries.
    Cause: nginx client_max_body_size default is 1 MB; multipart parsing needs
    the body streamed to disk; and naming an upload after its display name plus
    the minute it arrived makes a third file replace the second.
    Fix: client_max_body_size 2064m (2 GiB + 16 MiB of request framing — keep the
    number equal to the app's own cap, and test that they agree); spool to a temp
    file outside the served folder, enforce the cap while streaming, then finalise
    with a link(2) to a 128-bit random name so an overwrite is impossible, not
    merely unlikely; keep the display name as a label in the database; return 303
    (never 200) so a browser refresh does not re-upload; reserve ~512 MiB so the
    card can never fill up and take the portal down with it. Also block .apk
    downloads with a friendly page explaining that installing apps is not needed.

18. THE UNIT THAT RUNS BUT DOES NOT COME BACK AFTER A POWER CUT
    Symptom: everything works today; after a blackout the hotspot is missing.
    Cause: `systemctl start` with no `enable`, or a unit that depends on a
    network that is not up yet.
    Fix: enable AND --now for every unit; After=network-online.target +
    Wants=network-online.target for anything that touches the network; a boot
    guard unit that raises the hotspot if the home Wi-Fi did not appear within
    HOME_WIFI_TIMEOUT (default 75 s). The verify gate must assert
    `is-enabled` AND `is-active` — checking only one is how this bug ships.

19. A PATH UNIT THAT IGNORES FILES ALREADY THERE
    Symptom: dropping a book does nothing; dropping a second book works.
    Cause: .path units trigger on change, not on existing content.
    Fix: have the .service also run once at enable time (and make the importer
    treat "already imported" as success). Then the drop folder can never be
    "stuck" with an unprocessed file.

20. INJECTING THE SAME HTML TWICE
    Symptom: after re-running a phase, every manual page has two print buttons,
    or a CSS block is duplicated.
    Cause: append-if-missing without a marker.
    Fix: wrap injected markup in <!-- ark:print-link --> … <!-- /ark:print-link -->
    and skip the whole block when the marker exists; write file only when
    content actually changed. Proof: run the phase twice, grep count == 1.

21. ark.local WORKS ON THE MAC AND NOT ON THE PHONE
    Symptom: the hostname resolves on one device and times out on another.
    Cause: .local is mDNS (avahi); Android support is patchy and some routers
    block multicast.
    Fix: never rely on it. Advertise http://ark.lan (wildcard DNS from the
    hotspot) and http://10.42.0.1 everywhere, and put all three on the portal
    with a one-tap copy button.

22. "IT IS RUNNING" ≠ "IT SURVIVES A REBOOT"
    Symptom: three days later, one page 502s after a power blip.
    Cause: a service started by hand while debugging was never enabled.
    Fix: the verification gate reads systemctl is-enabled + is-active for every
    unit, curls every route, and writes a JSON receipt. Run it after every
    change, not once at the end.

23. LONG OPERATIONS THAT BLOCK THE SESSION
    Symptom: a 40-minute download, flash or apt run appears to hang and the
    session loses its result.
    Cause: foreground execution with no log.
    Fix: every long step runs in the background (nohup/systemd) writing to
    /srv/ark/logs or ~/Survival-Pi/logs, and the agent polls the log. The
    terminal must stay free for the next question.

24. macOS SHELL DIFFERENCES THAT WASTE AN HOUR
    Symptom: `du -sh --exclude=.git` errors, `sed -i` wants a backup suffix,
    `stat -c` fails.
    Cause: BSD userland, not GNU.
    Fix: use `sed -i ''`, `stat -f %z`, and avoid GNU-only flags in Mac-side
    scripts; keep Pi-side scripts GNU and separate. Also: everything under pi/
    and staging/ must be LF — verify with `file` before pushing.

25. THE MIRROR THAT FROZE, AND THE FILE THAT LIED ABOUT ITS SIZE
    Symptom: the queue looks alive — aria2 prints 3.8 MiB/s — but every .part
    sits at exactly 66,881 bytes and nothing finishes for hours. Days later a
    .zim of the "correct" size opens in kiwix as an unreadable bundle.
    Cause: two faults stacked. (a) The KiWix redirector hands out mirrors that
    collapse under parallel streams: 4 connections to mirror.download.kiwix.org
    froze at 66 KiB, while ONE connection to the same URL held 1-2 MiB/s. (b)
    aria2 trusts its .aria2 control file, so after being killed mid-write it
    "resumes" into pieces that were never written and leaves a full-size file
    full of holes (measured: 3,498,049,536 bytes nominal, 1,937,772,544 actually
    allocated) that no reader can open. A size-only "already have it" shortcut
    then marks that corpse as complete and never retries it.
    Fix: fetch single-stream — `wget -c` first, `curl -C -` second (both
    OpenSSL, both honest about resume); keep aria2 for generous mirrors only.
    Delete .part and .aria2 control files when a download is abandoned. And
    never trust size alone: compare `du -B1` (blocks on disk) with `stat -c %s`
    and treat anything below 98% as corrupt, then prove the bundle appears in
    library.xml before writing the "have" marker.
    Reporting, same file: the fetcher must run as a BACKGROUND job and a 5 s
    loop rewrites status.json every 15 s with `current_bytes` + `current_total`
    (the API turns those into a percent). Run the fetcher in the foreground and
    the home strip has nothing to say for the hour a 4 GiB bundle takes — that
    is how "is it stuck?" gets asked 20 times.

26. THE DEFAULT PASSWORD A STRANGER COULD REACH
    Symptom: an administration page answers from the hotspot, and its password
    is printed in the repository — because it has to be: the box is built
    before anyone owns it.
    Cause: a "bootstrap account" was treated as a login instead of as a
    hand-over. Serve the admin routes on the same origin as the portal and the
    well-known password becomes the box's real password.
    Fix: three locks, all cheap. (a) The public origin answers 404 for /admin.
    (b) The first claim requires the peer address to be loopback AND a header
    that only the loopback listener sets — the LAN listener blanks that header,
    so a forged one is ignored (the test suite asserts this). (c) `must_change`
    makes that first session good for nothing but setting a password, and a
    marker file kept OUTSIDE the database turns a wiped database into
    "recovery required" instead of a fresh default. Test it from a LAN
    address: a 403 on the setup step is the pass, not a bug.

27. THE GREEN DOT THAT COULD NOT BE WRONG
    Symptom: the home strip says the box is ready, the reader taps the library
    and gets an error; or a page that is merely empty is reported as broken.
    Cause: readiness was "a file exists". A dead reader leaves the file in
    place, so the dot stayed green, and an empty card looked like a fault.
    Fix: readiness is content AND a live answer. One module
    (pi/api/ark_health.py) decides, per part, with three outcomes: ready,
    empty (nothing on the card yet — amber, normal while filling up) and
    broken (content exists and the thing that serves it did not answer — red,
    with the reason and the next step). /api/ready answers 200 only when every
    part a reader needs answered, else 503 with the reasons. Prove it by
    stopping the reader on purpose: the row must turn to Not ready and name
    the fix. /api/health is NOT this verdict — it only says the backend
    answered.

28. THE NETWORK THAT ONLY EXISTED AT BOOT
    Symptom: the box is up, the portal answers on the box itself, and nothing
    can reach it. Wait ten minutes — nothing changes. Reboot and it works.
    Cause: the network was decided once, on the way up (a boot guard), so a
    router rebooted at eight in the evening left the box on a home network that
    no longer existed. The only cure was a human with a keyboard.
    Fix: ask the same question every minute. ark-net-watch (oneshot) under
    ark-net-watch.timer (OnBootSec=3min, OnUnitActiveSec=60s) reads: saved mode,
    any link up, hotspot up, home network in range, clients on the hotspot, and
    the owner's pin; then a pure decide() function returns stay, to-hotspot or
    to-home. Two rules are absolute: never take the hotspot away while a device
    is connected (and an uncountable station list means "somebody may be
    there"), and never overrule a choice a person made with ark-mode home /
    ark-mode hotspot (a pin in /etc/ark/mode.pinned; the watchdog's own rescue
    calls `ark-mode hotspot --auto`, which leaves no pin). Two lost checks
    before acting, three quiet ones before returning, and a 30-minute back-off
    after a return that failed — an access point that flaps is worse than one
    that stayed up. Prove it without touching the radio:
    `ark-net-watch --dry-run` prints what it sees and would do, and
    `--decide M L H R C P LOST BACK BLOCKED` prints only the decision, so the
    whole table is testable with no NetworkManager at all.

29. THE GAME SHELF THAT TRUSTED THE BROWSER
    Symptom: a game plays on the Mac and shows a blank screen on the box with
    the router unplugged; or a player's cookie reaches an owner page; or a
    stored game filename turns a download route into a file-read of something
    outside the games folder.
    Cause: the player loaded a script or font from a CDN; a password and a save
    were served from the same origin as the public portal; a header that marks
    the player origin was trusted when a visitor supplied it; a filename read
    from the database was joined to a path without proving it was a bare name.
    Fix: vendor the player (EmulatorJS 4.2.3 and its cores) under `/arcade/`
    so the page has no `http://` or `https://` asset reference at all. Put the
    player behind its own TLS origin on `:8445`; set `X-ARK-Player-Origin: 1`
    only there, and blank that header on the public `:80` location. Keep player
    tables and the `ark_player` cookie separate from administrators; `404`
    `/admin` on the player origin and make a player cookie useless there.
    Rebuild every game address from a validated slug and filename, and reject
    any stored name where `name != Path(name).name`. Prove it with the internet
    unplugged, a guest getting 401 from a save endpoint, and a player cookie
    failing to open `/admin`.

30. THE BACKUP THAT WAS NEVER READ BACK
    Symptom: a folder called `ark-backup-…` exists, so everyone relaxes; months
    later it refuses to restore, or the only copy dies with the card it was
    written to.
    Cause: the live database was copied with `cp` while it was in WAL mode; no
    manifest said what a complete folder looked like; a run that died left a
    half-written folder that looked finished; nobody ever ran the verify step;
    and the "backup" never left the card.
    Fix: take the database with SQLite's own `.backup`, never `cp`. Write the
    bundle as `<name>.partial`, put a sha256 and size for every file in a
    manifest, and publish it only by rename. Make `--verify` read every byte
    back, and make a restore prove the whole bundle before it touches anything,
    refuse an occupied box without `--force`, and never replace a shared file
    already there. Keep the newest two, take copies when something happened
    (no timer — a nightly copy can fill the card the box reads from), and copy
    the finished folder off the box. Give the owner a printed sheet that needs
    only a phone, a card reader and a working card.

31. THE SECOND HOUSE THE BOX HAD NEVER HEARD OF
    Symptom: the box is carried to another house (or onto a phone hotspot) and
    never appears on the network. Nothing is broken — it is a stranger there,
    and after a while the boot guard does what it is designed to do and starts
    broadcasting The-Ark-Offline, which looks like the fault rather than the
    fallback.
    Cause: only the networks in staging/wifi.env existed as profiles.
    NetworkManager can join nothing else. (The hotspot profile being absent from
    the air while the box sits on a home network is NOT a fault: ark-hotspot is
    autoconnect=no on purpose, and only ark-mode / ark-net-watch bring it up.)
    Fix: seed every network the box may ever live on, at build time, in
    WIFI_EXTRA_PROFILES (id|ssid|password|priority, priorities below the home
    slots so home still wins at home). On a box that is already running, add one
    without ever putting the password on a command line or into a shell history:
      sudo nmcli connection add type wifi ifname wlan0 con-name rodclan \
           ssid Rodclan autoconnect yes wifi-sec.key-mgmt wpa-psk
      sudo nmcli connection edit rodclan     # `set wifi-sec.psk` prompts, masked
    or write the file yourself through stdin (chmod 600 root:root, then
    `nmcli connection reload`) — never `nmcli ... wifi-sec.psk <password>`,
    which lands in history and in `ps`.
    The profile appears in /etc/NetworkManager/system-connections/ at 0600
    root:root. Prove it with
      nmcli -f 802-11-wireless.ssid,connection.autoconnect,connection.autoconnect-priority connection show rodclan
      ls -l /etc/NetworkManager/system-connections/
    — NOT by connecting, which moves the radio off the network you are testing
    over and can cut your own SSH session.

8. CONTENT: A CATALOGUE, NOT A LIST OF URLS
================================================================================

Hardcoding download URLs rots within months. Instead keep one TSV that names
what you want, and resolve real URLs from the public catalogue at build time.

  pi/kiwix/catalog.tsv   tabs, one row per bundle, 7 columns:
    flavour   maxi | nopic | mini | -
    label     the friendly name shown on the portal ("Medical encyclopedias")
    name      catalogue id → becomes <name>_<YYYY-MM>.zim on disk
    query     keyword sent to the catalogue to find this entry
    size_gib  last measured size, used for the disk budget
    tier      essential | core | extra   (download order AND profile)
    note      one plain-English line for the portal

  Profiles (pi/bin/ark-zim-resolve):
    mini = essential                     ~1 GiB   first hour on a small card
    core = essential + core              ~5 GiB   the sane default
    full = essential + core + extra      ~15 GiB  + optional 119 GiB wikipedia

  Row order matters: smallest-first inside each tier, so the library becomes
  useful within minutes instead of after the biggest file.

  The pipeline: ark-zim-resolve → /etc/ark/zim-queue.tsv (pinned URL + exact
  bytes) → ark-zim-download → wget -c single stream (resumable) → ark-kiwix-
  library rebuilds library.xml → kiwix-serve reloads. Each stage is idempotent
  and restartable.

  Two rules learned the hard way:
    · a bundle counts as present only when library.xml lists it (trap 7);
    · never let the queue exceed the free-space reserve (trap 10).

9. THE VERIFICATION GATE (pi/steps/90-verify.sh)
================================================================================

Read-only. Checks, then writes /srv/ark/ark_status.json and exits non-zero on
any failure. Categories:

  services    is-enabled AND is-active (or waiting/activating for the guard),
              for nginx, ark-api, ark-zim-downloader, ark-boot-guard,
              ark-net-watch.timer, ark-book-import.path, ark-arcade-discover.timer,
              ssh, NetworkManager, avahi-daemon, and
              ark-kiwix (soft when no bundles have arrived yet — an empty
              library is a normal state, not a bug)
  pages       HTTP codes for /, /help.html, /assets/ark.css, /search?q=water,
              /board, /files, /arcade/, /arcade/static/ark-arcade.css,
              /arcade/emulator/loader.js, /api/status, /vault/,
              /vault/quick-card.html, /generate_204, /kiwix/, /books/
  readiness   one line per part of the box, read from /api/ready: ready / empty /
              broken, with the reason the box itself gave.  Empty (nothing on
              the card yet) is soft — a box still filling up is not a fault.
              Content present but not serviceable is a failure.
  network     when mode=hotspot, the AP address is really on wlan0
  space       free space >= 5 GiB (hard floor; the reserve is 12)
  owner's door  /admin answers 404 on :80; :8443 answers; the loopback :8444
              listener answers; the Community and Games pages answer behind
              the sign-in; the recovery command is installed with the right
              mode; and the account count is reported (how many still hold a
              temporary password) without ever printing a secret
  game shelf  /arcade/ answers on :80; the player origin :8445 answers
              /arcade/player and 404 for /admin; games, player names and saves
              are counted; the last discovery line is reported
  file box    drop/files and drop/tmp exist, and the count of shared files is
              reported (a missing folder means phase 20 was skipped)
  content     collections on disk + titles indexed in library.xml, books in
              metadata.db, guides and printable PDFs
  receipt     JSON summary for the Mac: hostname, mode, ok, problems, ready,
              collections{files,gib,indexed}, books, guides{pages,pdfs},
              arcade{games,players,saves,player_origin}, free_gib, addresses

  Definition of done:
    □ zero ✗, and the closing line "everything a visitor touches is working",
      from `bash scripts/03-provision.sh <ip> --only 90-verify` (read the ✗
      column, not the total — the number of checks grows as the box does)
    □ a book dropped into the File Box is on the shelf within 60 s
    □ the same filename uploaded three times leaves three separate entries,
      three files on disk and an empty drop/tmp (proof the write path is fixed)
    □ one article opens inside /kiwix/ (not just the root page)
    □ one guide opens and its PDF prints
    □ /arcade/ plays with the internet unplugged; `:8445/arcade/player` answers
      with the box's certificate, a name keeps a save, and export/import works
    □ `sudo ark-backup --to /srv/ark/backup` writes a folder, `--verify` re-reads
      every byte, and `http://ark.lan/recovery.txt` prints
    □ services survive `sudo reboot` (cold-boot test done by a human who can
      join the hotspot — an agent over SSH cannot honestly claim this one)
    □ the receipt JSON says ok:true and the numbers match the card size

11. OPERATING RULES FOR THE AGENT (how to work, not just what to build)
================================================================================

  · Read before writing. Every claim about the box comes from a command's
    output in this session, not from memory or from what "should" happen.
  · Prove each phase with its own printed line. If you cannot print the proof,
    the phase is not done.
  · Long jobs (flash, apt, 119 GiB download, 5.7 GB rsync) run in the
    background with a log you poll. Never let the terminal block.
  · Idempotent or bust: content-compare before write, marker-guard before
    inject, tolerate already-running services.
  · All paths absolute. Never rely on $HOME inside something that runs as `pi`
    on the Pi.
  · `set -Eeuo pipefail` at the top of every bash script; `|| true` only with a
    comment explaining why.
  · `bash -n` every script before pushing; chmod +x anything executed.
  · LF only under pi/ and staging/.
  · On the Mac, wrap root commands in osascript (trap 2). Never write to a disk
    the guard has not blessed (trap 1).
  · When a doc and the code disagree, one of them is wrong — find out which,
    then fix the side that is actually broken. Do not paper over it by editing
    the sentence.
  · Prefer 20 small verified steps to 1 heroic one. If a step surprises you,
    stop and read the log before continuing.
  · Keep a changelog of bugs found while verifying. That list IS the value of
    this document.

12. MAKING COPIES FOR OTHER PEOPLE (three ways, best first)
================================================================================

  WAY 1 — RE-RUN THE PIPELINE (recommended)
    The repo is the blueprint. For each new Ark:
      a. copy the repo folder (or extract the tarball) to a new working dir
      b. edit staging/wifi.env (their home Wi-Fi) — never reuse someone else's.
         If the box will also live somewhere else (a relative's house, a phone
         hotspot), add that network in WIFI_EXTRA_PROFILES; a rebuilt card then
         joins it with nobody touching the Pi
      c. optionally edit /etc/ark/ark.env defaults for their hotspot name,
         channel, content profile and rate limit BEFORE first provision
      d. flash a fresh card, provision, verify
    Cost: one cheap SD card + a few hours of downloading per box. You get
    clean, explainable, upgradeable machines — and no secrets carried over
    from the previous owner.

  WAY 2 — CLONE A FINISHED CARD (fastest, fragile)
    dd the working card to an image, write it to another card.
      · shrink the filesystem first on a Linux box (parted/pishrink) or the
        image is useless on a smaller card
      · the clone carries the original's hostname, SSH host keys, Wi-Fi
        credentials and hotspot name — you MUST personalise afterwards
      · two clones on one network will fight over the same hostname
    Use it only for identical boxes in the same place (e.g. three units for
    one shelter), and change hostname + SSH keys + Wi-Fi profile on each.

  WAY 3 — CARRY THE CONTENT, NOT THE BOX
    The expensive part is 10-15 GiB of collections that take hours to fetch.
    Snapshot the content once onto a USB SSD:
      sudo rsync -a /srv/ark/kiwix/ /Volumes/ARK-CONTENT/kiwix/
      sudo rsync -a /srv/ark/calibre-library/ /Volumes/ARK-CONTENT/calibre-library/
      sudo rsync -a /srv/ark/vault/ /Volumes/ARK-CONTENT/vault/
    On the new box, restore into the same paths, chown -R pi:pi, then run
    phase 30 and 50 once to rebuild library.xml and re-apply permissions. This
    turns "two days" into "one hour" for every Ark after the first.

  KEEP THE BLUEPRINT ITSELF SAFE
    · `git init` this repo, commit, and tag v1.0. It is a text-only project
      (~330 KB of source); the only big things are staging/ (images) and
      logs/, both of which belong in .gitignore.
    · Keep one tarball off-machine (USB stick in the Ark's own box, or a
      friend's laptop):
        tar czf Project-ARK-$(date +%Y%m%d).tar.gz --exclude staging --exclude logs .
    · Keep this file inside the repo as docs/REBUILD-ME-ARK.txt, so the
      instructions and the code travel together and cannot drift apart.
    · Keep a copy of docs/USING-THE-ARK.md on a phone, and one taped inside
      the lid of the box. Paper survives what the Pi does not.

13. ASK THE HUMAN THESE SIX QUESTIONS FIRST (then stop and wait)
================================================================================

  1. Who is it for, and what do they actually need offline — medical, repairs,
     growing food, water, law, school, or "all of it"? (This picks the profile,
     which decides the card size.)
  2. What size SD card, and is there a second card for a backup? (128 GB → mini
     or core; 256 GB → full. Never size the card to fit Wikipedia maxi.)
  3. Whose Wi-Fi does it live on, and in which country? (SSID, PSK, regulatory
     country code for the radio.) Never reuse another household's credentials.
  4. What should the open network be called, and on what channel? (Default
     "The-Ark-Offline", ch 6 — but the name is often the only thing a person
     recognises, so let them choose.)
  5. Do they already have a Calibre library or a folder of books to adopt? If
     yes: where is it, how big, and what wrote it (version matters, trap 11).
  6. Who maintains it after handover — a person who will read
     docs/USING-THE-ARK.md, or nobody? (If nobody: prove the cold-boot failover
     and leave the paper quick-card in the box.)
